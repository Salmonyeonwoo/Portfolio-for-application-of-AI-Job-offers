1. プロジェクト概要: AI学習コーチとシミュレーター

主要機能

RAGベースQ&A、カスタムコンテンツ生成、LSTM予測

  • この範囲拡大が技術スタックの複雑化につながり、予期せぬ統合問題に直面しました。

2. LLMフレームワーク (LangChain) 設定の難関

問題 1: APIクライアントの初期化衝突

  • 困難点: Streamlit環境はセッション状態に基づき再実行(Rerun)される特性があり、@st.cache_resourceを使用してもOpenAI、LangChain ChatOpenAI、OpenAIEmbeddingsクライアントが衝突したり、不完全に初期化される問題が発生しました。
  • 特に、 init_openai_client関数を誤って呼び出したりセッション状態に保存したりすると、TypeErrorが発生し、LLM機能が麻痺しました。
  • 解決策: @st.cache_resourceを使用してOpenAIクライアントオブジェクトを一度だけ作成し、セッション状態に明示的に保存しました。また、LangChain LLMオブジェクトについても、APIキーの変更時にのみ再初期化されるよう、外部でキーの有効性を確認する方法を導入し、安定性を確保しました。

@st.cache_resource(ttl=3600, experimental_allow_widgets=True)
def init_llm_clients(openai_api_key):
    # Initialize OpenAI client (including LangChain)
    llm = ChatOpenAI(temperature=0.7, openai_api_key=openai_api_key)
    embeddings = OpenAIEmbeddings(openai_api_key=openai_api_key)
    # ... Initialize other LLM and embedding clients ...
    return llm, embeddings

if 'llm' not in st.session_state or 'embeddings' not in st.session_state:
    st.session_state.llm, st.session_state.embeddings = init_llm_clients(st.secrets["OPENAI_API_KEY"])

問題 2: LangChain ConversationChainとメモリ管理

  • 困難点: シミュレーター機能の複雑な会話フロー（顧客/エージェント）を管理するためにConversationChainとConversationBufferMemoryを使用しましたが、Streamlitのセッションリセットによりメモリが適切にクリアされなかったり、再実行のたびに履歴が重複し、LLMの応答が異常に長くなる問題が発生しました。
  • 解決策: 会話の開始/終了時にst.session_state.simulator_memory.clear()を明示的に呼び出し、LLMに渡すプロンプトテンプレートに現在の会話状態を手動で再構築（履歴を抽出してプロンプトに挿入）することで、LLMが正確なコンテキストのみを把握するようにしました。

# Memory initialization and management
if "simulator_memory" not in st.session_state:
    st.session_state.simulator_memory = ConversationBufferWindowMemory(k=5, memory_key="chat_history")

# Clear memory when starting a new conversation
if st.button("新しいシミュレーションを開始"):
    st.session_state.simulator_memory.clear()
    # ... Initialize other session states ...

# Inject memory into the LLM chain (consider manually including chat history in the prompt)
conversation_chain = ConversationChain(
    llm=st.session_state.llm,
    memory=st.session_state.simulator_memory,
    prompt=conversation_prompt # Custom prompt template
)

3. DB/ストレージ統合: データ永続性の確保

問題 3: LLM API Key取得の難関とFirebase先行導入の試み

  • 困難点 (LLM Key): プロジェクト開始時、他のチームメンバーとは異なり、私個人のOpenAI API Keyの取得が遅れたため（予算やセキュリティ上の理由）、LLMベースの機能（LangChain）開発を一時的に保留せざるを得ませんでした。
  • 困難点 (DB統合): 開発の継続性を確保するため、Firebase Admin SDKを先に統合してDB/GCS機能を実装する必要がありました。この過程で、StreamlitアプリがSDKを複数回初期化しようとし、ValueErrorエラーが発生しました。
  • 解決策 (DB): initialize_firestore_admin関数に、firebase_admin._appsをチェックし、アプリが既に初期化されている場合は**初期化をスキップする防御ロジック**を追加しました。
  • 解決策 (GCS): st.secretsからサービスアカウント情報をロードし、それを一時ファイルに書き込み、os.environ['GOOGLE_APPLICATION_CREDENTIALS']にパスを設定してからgoogle.cloud.storage.Client()を初期化するという標準的な方法を採用しました。

import firebase_admin
from firebase_admin import credentials, firestore
from google.cloud import storage
import json
import os

@st.cache_resource(ttl=3600)
def initialize_firebase_and_gcs():
    # Prevent duplicate Firebase Admin SDK initialization
    if not firebase_admin._apps:
        cred_info = json.loads(st.secrets["firestore_admin_sdk"])
        cred = credentials.Certificate(cred_info)
        firebase_admin.initialize_app(cred)
    db = firestore.client()

    # Initialize GCS client (saving secrets to file and setting path)
    with tempfile.NamedTemporaryFile("w", delete=False) as temp_file:
        temp_file.write(st.secrets["gcs_service_account"])
        temp_file_path = temp_file.name
    os.environ["GOOGLE_APPLICATION_CREDENTIALS"] = temp_file_path
    gcs_client = storage.Client()
    # Add logic to delete temp_file_path (upon app termination or appropriate time)

    return db, gcs_client

db, gcs_client = initialize_firebase_and_gcs()

問題 4: RAGインデックスの保存とロード

  • 困難点: ベクトルデータベースインデックス（FAISSなど）を直接DB（Firestore/GCS）に保存しようとすると、シリアル化/デシリアル化のエラーが発生し、特に大容量インデックスのDB保存は非効率的かつコストが高くなりました。
  • 解決策: DBの代わりにローカルファイルシステム（またはGCSバケット内の特定のフォルダ）に、FAISS.save_local()とFAISS.load_local()を使用してインデックスを保存/ロードする方法を採用しました。これにより、データ永続性を維持しつつ、LLM機能へのアクセス速度を最適化しました。

from langchain_community.vectorstores import FAISS

def save_faiss_index(index, path="faiss_index"):
    index.save_local(path)
    st.success(f"FAISS index saved to '{path}'.")

def load_faiss_index(embeddings, path="faiss_index"):
    if os.path.exists(path):
        loaded_index = FAISS.load_local(path, embeddings, allow_dangerous_deserialization=True)
        st.success(f"FAISS index loaded from '{path}'.")
        return loaded_index
    else:
        st.warning(f"No FAISS index found at '{path}'. Creating a new one.")
        return None # or logic to create a new index

5. 最終難関克服: クイズ安定化と多言語サポート

問題 5: クイズ完了時のIndexErrorとラジオボタンのエラー

  • 困難点: クイズの最終問題が完了し、スコア表示に移行する際に、Streamlitの再実行ロジックが完了前に範囲外のインデックスにアクセスしようとし、`IndexError: list index out of range`が発生しました。また、`st.radio`のインデックス初期化の問題もありました。
  • 解決策: クイズ完了の条件（`idx >= len(quiz_data)`）の直後にst.stop()を明示的に呼び出すことで、不要なインデックスアクセスを完全に阻止しました。さらに、ラジオボタンのインデックスエラーを解決するため、クイズの回答配列を安全な初期値（1）に設定しました。
  • 追加の問題: LLMにAPI構成を通じてJSON応答形式を強制する際、`unexpected keyword argument 'config'`といった互換性の問題が発生しました。
  • 解決策: 不安定なAPI configの代わりに、JSONスキーマを含む強力なシステムプロンプトをLLMに渡し、テキストベースでJSON応答を強制することで、問題を回避し安定性を確保しました。

# クイズ完了とIndexError防止ロジック (コア修正)
if idx >= len(quiz_data):
    st.success(L["quiz_complete"])
    total_questions = len(quiz_data)
    score = st.session_state.quiz_score
    st.subheader(f"{L['score']}: {score} / {total_questions} ({(score / total_questions) * 100:.1f}%)")

    if st.button(L["retake_quiz"], key="retake_quiz_btn"):
        # State Initialization
        st.session_state.is_quiz_active = False
        st.session_state.quiz_data = None
        st.session_state.current_question_index = 0
        st.session_state.quiz_score = 0
        st.session_state.quiz_answers = []
        st.session_state.show_explanation = False
        st.rerun() # Force rerun after state initialization
    st.stop() # 必須: 完了チェック後、スクリプトの実行を直ちに停止

結論と今後の計画

LLMプロジェクトは単にコードを書くだけでなく、外部サービスの統合と環境的な制約を乗り越えるプロセスでした。 特に、Streamlitの非同期的な性質とLangChainのクライアント依存性を理解することが鍵となりました。

最大の教訓: 「小さな機能であっても、環境変数と初期化の順序に関する徹底的な防御ロジックが不可欠である。」
