2. LLM 프레임워크 (LangChain) 설정 난관

문제 1: API 클라이언트 초기화 충돌

  • 어려움: Streamlit 환경은 세션 상태를 기반으로 재실행(Rerun)되는 특성이 있어, @st.cache_resource를 사용하더라도 OpenAI, LangChain ChatOpenAI, OpenAIEmbeddings 클라이언트가 충돌하거나 불완전하게 초기화되는 문제가 발생했습니다.
  • 특히, init_openai_client 함수를 잘못된 방식으로 호출하거나 세션 상태에 저장할 때 TypeError가 발생하여 LLM 기능이 완전히 마비되었습니다.
  • 해결: @st.cache_resource를 사용하여 OpenAI 클라이언트 객체를 한 번만 생성하고, 이를 세션 상태에 명시적으로 저장했습니다. 또한, LangChain LLM 객체도 API 키 변경 시에만 재초기화되도록 외부에서 키 유효성을 확인하는 방식을 도입하여 안정성을 확보했습니다.

@st.cache_resource(ttl=3600, experimental_allow_widgets=True)
def init_llm_clients(openai_api_key):
    # OpenAI 클라이언트 초기화 (LangChain 포함)
    llm = ChatOpenAI(temperature=0.7, openai_api_key=openai_api_key)
    embeddings = OpenAIEmbeddings(openai_api_key=openai_api_key)
    # ... 다른 LLM 및 임베딩 클라이언트 초기화 ...
    return llm, embeddings

if 'llm' not in st.session_state or 'embeddings' not in st.session_state:
    st.session_state.llm, st.session_state.embeddings = init_llm_clients(st.secrets["OPENAI_API_KEY"])

문제 2: LangChain ConversationChain 및 메모리 관리

  • 어려움: 시뮬레이터 기능에서 고객/에이전트의 복잡한 대화 흐름을 관리하기 위해 ConversationChain과 ConversationBufferMemory를 사용했는데, Streamlit의 세션 리셋 시 메모리가 제대로 비워지지 않거나, 재실행 시마다 이전 대화 이력이 중복되어 LLM의 응답이 비정상적으로 길어지는 문제가 있었습니다.
  • 해결: 대화 시작/종료 시 st.session_state.simulator_memory.clear()를 명시적으로 호출하고, LLM에 전달하는 프롬프트 템플릿에 현재 대화 상태를 수동으로 재구성하여 (대화 내용 추출 후 프롬프트에 삽입) LLM이 정확한 맥락만 파악하도록 했습니다.

# 메모리 초기화 및 관리
if "simulator_memory" not in st.session_state:
    st.session_state.simulator_memory = ConversationBufferWindowMemory(k=5, memory_key="chat_history")

# 새로운 대화 시작 시 메모리 초기화
if st.button("새로운 시뮬레이션 시작"):
    st.session_state.simulator_memory.clear()
    # ... 다른 세션 상태 초기화 ...

# LLM 체인에 메모리 주입 (대화 히스토리를 직접 프롬프트에 포함하는 방식도 고려)
conversation_chain = ConversationChain(
    llm=st.session_state.llm,
    memory=st.session_state.simulator_memory,
    prompt=conversation_prompt # 사용자 정의 프롬프트 템플릿
)

3. DB/스토리지 통합: 데이터 영속성 확보

문제 3: LLM API Key 확보 난관과 Firebase 선행 시도

  • 어려움 (LLM Key): 프로젝트 초기에 다른 팀원들과 달리 저 개인의 OpenAI API Key 발급이 늦어지면서 (예산 및 안정성 확보 문제), LLM 기반 기능(LangChain) 개발을 잠시 보류해야 했습니다.
  • 어려움 (DB 통합): 이로 인해 개발 연속성을 위해 Firebase Admin SDK를 먼저 통합하여 DB/GCS 기능을 구현해야 했고, 이 과정에서 Streamlit 앱에서 SDK를 여러 번 초기화하려는 시도로 인해 ValueError 오류가 발생했습니다.
  • 해결 (DB): initialize_firestore_admin 함수에, firebase_admin._apps를 확인하여 이미 초기화된 경우를 건너뛰는 방어 로직을 추가했습니다.
  • 해결 (GCS): 서비스 계정 정보를 st.secrets에서 로드하여 임시 파일로 작성하고, os.environ['GOOGLE_APPLICATION_CREDENTIALS']에 해당 경로를 설정한 후 google.cloud.storage.Client()를 초기화하는 표준 방식을 사용했습니다.

import firebase_admin
from firebase_admin import credentials, firestore
from google.cloud import storage
import json
import os

@st.cache_resource(ttl=3600)
def initialize_firebase_and_gcs():
    # Prevent duplicate Firebase Admin SDK initialization
    if not firebase_admin._apps:
        cred_info = json.loads(st.secrets["firestore_admin_sdk"])
        cred = credentials.Certificate(cred_info)
        firebase_admin.initialize_app(cred)
    db = firestore.client()

    # Initialize GCS client (saving secrets to file and setting path)
    with tempfile.NamedTemporaryFile("w", delete=False) as temp_file:
        temp_file.write(st.secrets["gcs_service_account"])
        temp_file_path = temp_file.name
    os.environ["GOOGLE_APPLICATION_CREDENTIALS"] = temp_file_path
    gcs_client = storage.Client()
    # Add logic to delete temp_file_path (upon app termination or appropriate time)

    return db, gcs_client

db, gcs_client = initialize_firebase_and_gcs()

문제 4: RAG 인덱스 저장 및 로드

  • 어려움: FAISS와 같은 벡터 데이터베이스 인덱스를 DB에 직접 저장하는 과정(Firestore/GCS)에서 데이터 직렬화/역직렬화 오류가 발생했고, 특히 대용량의 인덱스를 DB에 저장하는 것은 비효율적이고 비용적 부담이 컸습니다.
  • 해결: DB 대신 로컬 파일 시스템 (혹은 GCS 버킷 내 특정 폴더)에 FAISS.save_local()과 FAISS.load_local()을 사용하여 인덱스를 저장/로드하는 방식을 채택했습니다. 이는 데이터 영속성을 유지하면서도 LLM 기능에 대한 접근 속도를 최적화했습니다.

from langchain_community.vectorstores import FAISS

def save_faiss_index(index, path="faiss_index"):
    index.save_local(path)
    st.success(f"FAISS 인덱스가 '{path}'에 저장되었습니다.")

def load_faiss_index(embeddings, path="faiss_index"):
    if os.path.exists(path):
        loaded_index = FAISS.load_local(path, embeddings, allow_dangerous_deserialization=True)
        st.success(f"FAISS 인덱스가 '{path}'에서 로드되었습니다.")
        return loaded_index
    else:
        st.warning(f"'{path}' 경로에 FAISS 인덱스가 없습니다. 새로 생성합니다.")
        return None # 또는 새로운 인덱스 생성 로직

문제 5: 퀴즈 완료 시 IndexError 발생 및 라디오 버튼 오류

  • 어려움: 퀴즈의 마지막 문항을 풀고 점수 표시로 전환될 때, Streamlit의 재실행 로직이 완료 전에 다음 문항에 접근하려 시도하며 `IndexError: list index out of range` 오류가 발생했습니다. 또한, `st.radio`의 인덱스 초기화 문제도 있었습니다.
  • 해결: 퀴즈 완료 조건(`idx >= len(quiz_data)`) 직후 `st.stop()`을 명확히 호출하여 불필요한 인덱스 접근을 완전히 차단했습니다. 또한, 퀴즈 답변 배열을 안전한 초기값(1)로 설정하여 라디오 버튼 오류를 해결했습니다.
  • 추가 문제: LLM에게 JSON 응답 형식을 강제하는 과정에서 `google.generativeai` 라이브러리의 `config` 인자 호환성 문제가 발생했습니다.
  • 해결: 불안정한 `config` 인자 대신, LLM에게 **JSON 스키마를 포함한 강력한 시스템 프롬프트**를 전달하여 텍스트 기반으로 JSON 응답을 강제하는 방식으로 우회하여 안정성을 확보했습니다.

# 퀴즈 완료 및 IndexError 방지 로직 (핵심 수정)
if idx >= len(quiz_data):
    st.success(L["quiz_complete"])
    total_questions = len(quiz_data)
    score = st.session_state.quiz_score
    st.subheader(f"{L['score']}: {score} / {total_questions} ({(score / total_questions) * 100:.1f}%)")

    if st.button(L["retake_quiz"], key="retake_quiz_btn"):
        # 상태 초기화
        st.session_state.is_quiz_active = False
        st.session_state.quiz_data = None
        st.session_state.current_question_index = 0
        st.session_state.quiz_score = 0
        st.session_state.quiz_answers = []
        st.session_state.show_explanation = False
        st.rerun() # 상태 초기화 후 즉시 재실행
    st.stop() # 퀴즈 완료 후 스크립트 실행을 완전히 중단
